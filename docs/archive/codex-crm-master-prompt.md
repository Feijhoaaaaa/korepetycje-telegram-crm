# Технический промпт для Codex: аудит, исправление и развитие Telegram CRM для преподавателей

## 1. Контекст проекта

Проект — CRM-система для преподавателей платных языковых занятий, в первую очередь курсов польского языка.

Система состоит из:

- Telegram-бота на Python;
- Telegram Mini App;
- backend-логики;
- базы данных Supabase;
- системы учеников и преподавателей;
- расписания занятий;
- доступности учеников и преподавателей;
- заявок на перенос/отмену занятий;
- учёта оплат;
- уведомлений и напоминаний;
- профилей и пользовательских настроек.

Проект уже существует и частично работает. Не нужно переписывать его с нуля без необходимости. Сначала изучи текущую архитектуру, код, структуру БД и связи между компонентами, затем внеси минимально необходимые, но системные исправления.

Главные цели:

1. Исправить существующие баги.
2. Сделать архитектуру устойчивой к повторным запросам, двойным кликам и параллельным действиям.
3. Довести до рабочего состояния расписание, заявки, платежи, профили и Mini App.
4. Упростить дальнейшую поддержку проекта.
5. Не ломать уже работающие функции без необходимости.

## 2. Общий порядок работы

Перед внесением изменений:

1. Проанализируй структуру репозитория.
2. Найди точки входа backend, Telegram-бота и Mini App.
3. Найди все модели/таблицы Supabase и миграции.
4. Найди весь код, отвечающий за:
   - пользователей;
   - учеников;
   - преподавателей;
   - расписание;
   - доступность;
   - платежи;
   - уведомления;
   - Mini App;
   - конфигурацию;
   - запуск приложения.
5. Определи существующие проблемы архитектуры и дублирование логики.
6. Составь краткий план изменений.
7. Только после этого начинай редактирование.

Не делай большой rewrite, если проблема решается безопасным рефакторингом существующего кода.

После каждого крупного блока изменений:

- запускай тесты;
- добавляй недостающие тесты;
- проверяй ошибки;
- проверяй целостность БД;
- проверяй повторные запросы;
- проверяй конкурентные сценарии;
- обновляй документацию.

# 3. Работа с Graphify и контекстом проекта

Проект должен использовать Graphify как постоянный knowledge graph репозитория, чтобы Codex не перечитывал весь проект при каждой задаче.

Правила работы:

1. Перед широким поиском по репозиторию сначала используй Graphify.
2. Через Graphify определяй:
   - релевантные файлы;
   - символы;
   - функции;
   - callers/callees;
   - зависимости;
   - связи между компонентами;
   - blast radius предполагаемого изменения.
3. После получения результатов Graphify обязательно прочитай реальные исходные файлы перед их изменением.
4. Graphify — индекс и навигационный слой, но не источник истины вместо кода.
5. После структурных изменений обновляй/переиндексируй граф.
6. Не перечитывай весь репозиторий без необходимости.
7. Старайся сначала сузить задачу до минимального набора файлов.
8. Для архитектурных изменений сначала анализируй зависимости и возможные побочные эффекты.

Желаемый workflow:

```text
задача
→ Graphify
→ определение 2–10 релевантных файлов/символов
→ чтение реального кода
→ изменение
→ тесты
→ обновление Graphify
```

# 4. Архитектура запуска

## 4.1. Production-архитектура

Не проектируй систему так, чтобы каждый преподаватель запускал отдельную копию одного и того же Telegram-бота.

Production-режим должен предполагать:

- один централизованный backend;
- один Telegram-бот;
- один Bot Token;
- один Mini App;
- одну общую базу Supabase;
- множество преподавателей;
- множество учеников;
- разграничение данных по пользователям;
- роли и права доступа.

Целевая схема:

```text
Telegram / Telegram Mini App
        ↓
централизованный backend
        ↓
Supabase
```

Если backend разворачивается serverless, ориентируй Telegram-бота на webhook, а не на бесконечный long polling.

Не используй `while True`, долгоживущие локальные таймеры или `sleep()` как механизм production-планировщика.

---

## 4.2. Локальный режим

Локальный запуск оставить для:

- разработки;
- тестирования;
- отладки;
- административных задач при необходимости.

Если локальная сборка всё ещё используется преподавателем/администратором, защити её от запуска нескольких конфликтующих экземпляров.

# 8. Управление учениками

Сейчас есть проблемы:

- уже добавленный тестовый ученик иногда не определяется системой;
- система предлагает добавить его повторно;
- повторное добавление может создать дубликат;
- ученика нельзя нормально удалить;
- нет понятного полного жизненного цикла записи ученика.

Проведи полный аудит workflow ученика.

## 8.1. Добавление

Добавление должно быть идемпотентным.

Один и тот же ученик не должен создаваться дважды из-за:

- двойного клика;
- повторного webhook;
- повторной команды;
- сетевого retry;
- параллельного запроса.

Добавить уникальные ограничения на уровне БД там, где это логически необходимо.

Например, комбинация:

```text
teacher_id + telegram_user_id
```

или другая корректная модель после анализа текущей архитектуры.

Не полагаться только на frontend-проверку.

---

## 8.2. Существующий ученик

Перед созданием нового ученика:

1. проверить существующую запись;
2. определить активный/архивный статус;
3. корректно восстановить или привязать запись при необходимости;
4. не создавать дубль.

---

## 8.3. Редактирование

Добавить нормальное редактирование ученика:

- имя;
- контактные данные;
- язык;
- валюта;
- заметки;
- настройки;
- статус;
- прочие существующие поля.

---

## 8.4. Удаление и архивирование

Реализовать:

- `archive`;
- `restore`;
- при необходимости `hard delete`.

По умолчанию предпочтительно архивирование, если у ученика существуют:

- завершённые уроки;
- платежи;
- финансовая история;
- заявки;
- другие связанные сущности.

Hard delete разрешать только если это безопасно.

Не уничтожать финансовую и учебную историю случайным удалением записи.

# 9. Защита от двойных кликов и повторных операций

Это критический блок.

Сейчас из-за медленного ответа приложения двойное нажатие может отправить две команды и выполнить одно действие дважды.

Исправить системно.

На frontend:

- после отправки действия временно блокировать кнопку;
- показывать loading state;
- предотвращать повторный submit;
- восстанавливать кнопку после ответа/ошибки;
- использовать debounce только там, где он уместен.

На backend:

- все критические команды должны быть идемпотентными;
- использовать idempotency key / request key, где это уместно;
- проверять текущее состояние записи;
- использовать уникальные ограничения;
- использовать транзакции;
- корректно обрабатывать race condition;
- повторный одинаковый запрос не должен создавать второй объект.

Критические сценарии:

- создание ученика;
- создание платежа;
- подтверждение платежа;
- создание заявки;
- подтверждение переноса;
- отмена занятия;
- создание занятия;
- отправка напоминаний.

# 12. Предложение времени учеником

Ученик должен иметь возможность самостоятельно предложить время занятия.

Workflow:

1. Ученик открывает расписание.
2. Система показывает совместимые свободные интервалы.
3. Ученик выбирает слот или предлагает другое время.
4. Создаётся заявка со статусом `pending`.
5. Преподаватель получает заявку.
6. Преподаватель:
   - подтверждает;
   - отклоняет;
   - предлагает другое время.
7. Если преподаватель предложил другой слот, заявка возвращается ученику на подтверждение.
8. Только после подтверждения создаётся/изменяется занятие.

Не менять расписание до финального подтверждения.

# 15. Напоминания по необработанным заявкам

Если заявка остаётся `pending`, преподавателю должны приходить напоминания.

Базовый сценарий:

- первое напоминание через 1 час;
- второе через 3 часа;
- дальнейшие интервалы должны быть конфигурируемыми.

Добавить кнопку:

```text
Напомнить позже
```

с вариантами, например:

- через 1 час;
- через 3 часа;
- завтра.

После:

- `approved`;
- `rejected`;
- `cancelled`;
- `expired`;

новые напоминания не отправлять.

Не использовать `sleep()` или долгоживущие Python timers.

Хранить состояние в Supabase.

Например:

```text
next_reminder_at
last_reminder_at
reminder_count
```

Периодическая задача должна находить просроченные pending-заявки и отправлять уведомления.

Защитить от повторной отправки одним и тем же scheduler run.

# 16. Платежи

Переработать систему платежей.

Не пытаться автоматически определять сумму только по фотографии чека.

Основной workflow:

1. Ученик запускает `/pay`.
2. Бот предлагает валюту.
3. Ученик выбирает валюту.
4. Бот спрашивает сумму.
5. Ученик отправляет фотографию или файл подтверждения.
6. Создаётся платёж со статусом `pending`.
7. Бот автоматически копирует/отправляет подтверждение преподавателю.
8. Преподаватель проверяет данные.
9. Преподаватель:
   - подтверждает;
   - исправляет сумму/валюту;
   - отклоняет.
10. Только подтверждённый платёж учитывается финансовой системой.

# 20. Финансовый журнал

Не хранить всю финансовую историю только в изменяемом поле `balance`.

Реализовать журнал операций.

Минимальные типы операций:


Баланс должен:

- либо вычисляться из подтверждённых операций;
- либо обновляться транзакционно вместе с финансовой записью.

Нельзя изменять баланс без создания соответствующей операции в журнале.

---

# 21. Несколько валют

Не смешивать валюты напрямую.

Нельзя считать:

```text
100 PLN + 500 UAH
```

одним балансом.

Варианты:

1. отдельный баланс для каждой валюты;
2. базовая валюта преподавателя с явной конвертацией.

Если реализуется конвертация, сохранять:

- `original_amount`;
- `original_currency`;
- `exchange_rate`;
- `converted_amount`;
- `accounting_currency`;
- дату фиксации курса.

Старые операции нельзя пересчитывать по новому курсу.

# 22. Защита платежей от повторной обработки

Критически важно:

- двойное нажатие `Подтвердить` не должно дважды увеличить баланс;
- повторный webhook не должен создать второй платёж;
- повторная отправка одного действия не должна задублировать запись;
- конкурентное подтверждение должно корректно обрабатываться.

Использовать:

- транзакции;
- row state validation;
- уникальные ограничения;
- idempotency;
- atomic update/locking, где необходимо.
